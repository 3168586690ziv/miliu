# 密流第 3 / 4 阶段施工建议（历史方案）

后续状态：第 3 阶段已按授权施工，参见 [测试分级验收](<docs/AI-Reports/密流第3阶段测试分级验收-20261110.md>)；第 4 阶段真实源码调查见 [落地调查](<docs/AI-Reports/密流第4阶段源码落地调查-20261110.md>)。以下为原始决策前建议，不代表当前全部未施工。

## 第 3 阶段：结果分级与真实生产链守卫

### 建议写范围

- [run-suites.sh](tests/Tests/run-suites.sh)：汇总 PASS / FAIL / SKIP / ENVIRONMENT，不再把 exit=0 且缺关键段的套件称为全部通过。
- [preview-playback.sh](tests/Tests/preview-playback.sh)：各段输出结构化状态；缺带编码器 ffmpeg 属 ENVIRONMENT，不是产品 FAIL，也不是 E2E PASS。
- [PreviewE2E.m](tests/Tests/PreviewE2E.m)：后续接入生产控制器，而不是自建“等价”播放器。现有解码/请求日志断言全部保留。
- 保留 [PreviewControllerTests.m](tests/Tests/PreviewControllerTests.m)、[PreviewLifecycleTests.m](tests/Tests/PreviewLifecycleTests.m) 作为不依赖 GUI / ffmpeg 的必跑生产守卫。
- 新增独立跑器分级测试；只运行临时目录里的人工夹具脚本，不启动 App，不运行真实 AVPlayer。

### 具体规则

1. 建议统一结果行（或结果 JSON 文件）：suite、stage、status、reason。状态四种：PASS / FAIL / SKIP / ENVIRONMENT。编译失败、断言失败固定 FAIL；主动未选段为 SKIP；缺依赖为 ENVIRONMENT。
2. 可保留传统退出码；新套件约定 0=完整 PASS、1=FAIL、77=SKIP、78=ENVIRONMENT。混合套件若纯逻辑通过但 E2E 未运行，整套状态不可 PASS，同时保留各段结果。
3. 普通模式允许环境不足继续跑，但必须输出 `COMPLETED_WITH_SKIPS` 等不冒充全通过的结论；只有所有必选段确实 PASS 才输出 `ALL SUITES PASSED`。
4. 增加发布严格模式：关键 E2E 出现 SKIP / ENVIRONMENT 均令整次验收非零退出，并列出缺失能力；不把依赖缺失诊断成产品缺陷。
5. 旧脚本过渡期先识别行首 `SKIP:`；最终以结构化状态为准，避免被夹具文本里的“SKIP”误导。缺失脚本、未知状态和编译失败不得被跳过标记掩盖。
6. 跑器测试使用临时小仓库与 PASS / FAIL / SKIP / ENVIRONMENT / 混合 / 缺失 / 信号退出夹具，验证普通和严格模式退出码、汇总及日志保留。它不需要 GUI、ffmpeg、用户数据或外网。

### 真实预览 E2E 的实施边界

当前生产控制器测试替换网络、播放器、窗口边界；环回 HTTP 测试是真的生产本地服务器，但不是 AVPlayer 解码验收。下一阶段可先完成跑器分级与生产控制器接线；真实 AVPlayer 段仍应单独记录“已跑 / 环境不足 / 未授权”。若要做无窗口真实播放器测试，先增加仅测试构建的窗口接收器，使用本地临时媒体与随机环回端口。不得启动主 App，也不能把窗口透明化当作允许弹窗的理由。

## 第 4 阶段：认证、第三方翻译、证书

### A. 认证上下文：先收窄目标，不复制整份 Cookie

现状：导入登录态供 WebKit 探测使用，不等于原生下载和预览已获得认证。第 2 阶段已修复结构化 HTTP 401 诊断，但未擅自桥接认证。

**建议最小实施顺序：**

1. 先保持默认无 Cookie 的原生链路，新增“探测登录态不自动等于原生媒体认证”的技术能力说明及受控测试，不改设置页。
2. Lead 若批准真正支持认证下载，再做单独的内存认证上下文提供器，按一次用户发起的下载取值；来源和目标必须明确同源，按 host/domain、path、Secure、有效期筛选。不持久化 Cookie，不写全局 Cookie jar，不打印值；跨域重定向只剥离、不从初始请求恢复。
3. 提供器须注入到真实请求构造链，并覆盖流清单、分片、密钥、重定向；只修首个请求不算完成。下载会话继续隔离全局 Cookie / credential storage。
4. 不给 AVPlayer 资产级固定头注入 Cookie / Authorization：其未知 HLS 子请求与重定向无法同源约束，问题与 FullPath Referer 相同。若要完整认证预览，需要另立逐请求受控方案，不能本轮顺手扩大。

**候选生产落点：** [DownloadManager.m 中的 SessionDownloadBackend](src/Features/ResourceDownload/DownloadManager.m#L171) 及流请求构造链；导入器 [RDCdpCookieImporter.m](src/Features/ResourceDetector/RDCdpCookieImporter.m) 不应改成向所有 native 请求批量灌 Cookie。实施前由 Lead 选择是否扩大到认证下载。

**行为变化：** 一旦启用桥接，原来匿名的部分下载会以用户会话身份请求；账号相关、跨域或分区 Cookie 不应被自动外推。默认保持无 Cookie 不会新增外发面，但不会解决需认证的原生媒体下载。

**测试：** 注入人工 Cookie 列表和假 HTTP transport，验证同源允许、域/路径/过期/HTTPS 限制、跨站剥离、重定向回原站不复活、取消后不回流。不读真实 WebKit 存储或浏览器。

### B. 翻译：建议可注入的外发许可，默认本地模式需 Lead 拍板

现状：[ResourceTitleTranslator.m](src/Features/ResourceDetector/ResourceTitleTranslator.m) 会把标题放入第三方 GET 请求的 `q` 参数。把 GET 改 POST 不能消除“标题交给第三方”这一根本事实。

**建议小改：** 在翻译器入口增加可注入许可判断；未许可时只用现有本地字典回退，不能本地处理则保留原题，异步 completion 仍按原契约调用。许可后才允许第三方请求；缓存已有译文可继续复用，不新增外发。无需修改 App 页面，也无需弹授权窗。

- 推荐隐私方案：新许可默认关闭，显式技术配置后才开启；现有“无许可即自动外发”停止。它会改变非中文标题的自动翻译覆盖率，必须由 Lead 明确接受。
- 保持行为方案：默认继续开启，只增加可配置关闭能力及精确测试。改动小，但不能声称已解决默认外发风险。
- 重点文件限于翻译器及其协调器/测试；不先改 App 页面或设置页。许可注入用于测试，不能用真实用户默认项作为测试开关。

**测试：** 注入 NSURLProtocol 捕获器：未许可请求数严格为 0、原题/本地回退仍完成；许可后请求字段准确；中文短路零请求；取消与重复翻译不串回调。只使用假标题，不触外网。

### C. TLS：建议保留窄容错代码，严格默认属于明确行为变更

现状：[RDTLSTrust.h](src/Shared/Infrastructure/RDTLSTrust.h) 对“吊销 leaf”的窄容错默认开启，历史上确实为特定站点恢复过可用性；[Info.plist](src/Packaging/Info.plist) 的 ATS 例外仍在。当前阶段两者均未修改。

**建议可执行方案：** 把缺省许可改为严格系统信任，保留已有显式开关的窄容错分支，且仍须满足索引、SAN、仅 leaf 等现有判据。不能把默认严格与删除容错混为一谈，也不能在同一次小改里无证据地移除 ATS 例外。

- 行为变化：没有显式偏好值的现有用户也会转严格，过去靠吊销容错才能访问的站点可能失败。不能声称零兼容成本。
- 若 Lead 本轮不接受该成本：先保持默认值，只做默认/显式开关的真实生产测试、能力披露和后续明确决策；不要静默改证书默认。
- 测试应使用可注入的配置读取和本地证书夹具，保持 SAN / 中间 CA / 域名不符 / 过期等原断言，不能直接改真实用户偏好或靠真实站点在线测试来判定纯策略正确性。

## 建议 Lead 的下一步顺序

先实施第 3 阶段（跑器分级与发布严格模式），再集中决定第 4 阶段三项的产品行为：认证是否新增同源下载桥接、翻译是否默认本地、TLS 是否缺省严格。三项均可不新增 UI，但不是三项都能宣称对既有用户行为完全无影响。
